# RunnerMesh v0.1 Design Freeze

Status: **Accepted design baseline for v0.1 implementation**

RunnerMesh v0.1 is the first usable release: a Windows, single-workstation, user-session admission controller for an already-configured official GitHub Actions self-hosted runner. It is intentionally designed to remain useful if later versions are delayed for a long time.

This document is the detailed product contract for v0.1. The ADRs under `docs/adr/`, governance under `dev_governance_files/`, and implementation roadmap under `goals/` refine it. A Goal that needs to change a frozen decision must do so through an explicit ADR rather than silently broadening scope.

## 1. Product outcome

```text
Windows sign-in
  -> RunnerMesh agent starts in the ordinary user session
  -> tray icon appears
  -> Auto Lite evaluates local evidence
  -> idle/away machine contributes CI
  -> active or latency-sensitive machine drains new CI
  -> the user can override policy from tray or CLI
```

The product should be install-once, configure-once, and mostly forgettable.

## 2. v0.1 must-have surface

v0.1 includes:

- ordinary-user persistent Agent;
- Windows system tray as the primary daily UI;
- CLI for scripting, diagnostics, and advanced control;
- local Named Pipe IPC;
- atomic, schema-versioned persisted intent/configuration;
- explicit modes: `auto`, `work`, `gaming`, `idle`, `maintenance`, `force-ci`;
- a persistent Zen override above `UserMode`;
- Activity/Workload Probe abstraction;
- User Activity Probe;
- Steam Game Probe;
- configurable Process List Probe;
- conservative Auto Lite policy;
- `status`, `doctor`, `version`, runner/probe inspection, and stable JSON;
- official runner observation and supervision;
- GitHub-native dynamic admission through the reserved `runnermesh-admit`
  custom label;
- explicit desired-versus-achieved two-phase drain semantics;
- runner restart/reconnect/adoption;
- host CPU/memory/idle/session observation;
- typed GitHub Actions link state;
- user-session start on login;
- crash/restart reconciliation;
- version/provenance reporting;
- user-level installation;
- immutable version slots, staged activation, health-checked rollback, and update checking;
- Windows x64 release artifacts plus SHA-256 checksums.

## 3. Explicit non-goals

v0.1 does **not** implement:

- real `THROTTLED` resource enforcement, Job Objects, CPU-rate control, EcoQoS, or memory enforcement (v0.2);
- broad game/application intelligence, GPU heuristics, foreground-app classification, or complex hysteresis/cooldown (v0.3);
- multi-node mesh placement (v0.4);
- disposable/VM execution (v0.7);
- Linux backend (v0.8);
- broker, JIT registration, or scale-set integration (v0.9);
- TUI, full GUI settings window, Web UI, custom GitHub runner protocol, workflow scheduler, or CI-data proxy.

`THROTTLED` remains a stable vocabulary value from G01, but v0.1 must not claim native throttling behavior.

## 4. Runtime topology

```text
Windows interactive user session

  runnermesh CLI ---------\
                          >-- Named Pipe --> RunnerMesh Agent
  tray frontend ----------/                    |
                                               | Observe
                                               | Decide
                                               | Reconcile
                                               v
                                      official Runner.Listener
                                               |
                                      official Runner.Worker
                                               |
                                         outbound HTTPS
                                               |
                                             GitHub
```

CLI and Tray are frontends. The Agent Core is the sole operational authority. Frontends never directly start/kill the runner, mutate work roots, or own policy state.

The architectural loop is `Observe -> Decide -> Reconcile -> Observe`.

Exactly one controlling Agent may exist per user profile. A user-scoped named mutex or equivalent single-instance guard must prevent stable/canary dual authority.

## 5. Runtime contracts

G02 must define stable contracts for at least:

- `RunnerPhase`: `Stopped`, `Starting`, `Listening`, `Busy`, `DrainPending`, `Stopping`, `Unknown`;
- `AdmissionDecision` including allow/deny, desired state, reason code, and drain intent;
- `ZenOverride`;
- `AgentHealth`;
- `LinkState` and `LinkSnapshot`;
- `ProbeRuntimeState` and `ProbeSnapshot`;
- `AgentSnapshot`;
- `AgentCommand` / `AgentResponse`;
- `UiPreferences`.

`NodeState::DRAINED` does not imply `RunnerPhase::Stopped`: the exact Listener
may remain connected but ineligible after selector withdrawal. An existing or
racing active job is represented as drain-pending/withdrawing until its Worker
finishes; achieved `DRAINED` never hides an active bound Worker.

## 6. Human-first precedence

Policy precedence is:

```text
hard safety
  > Zen override
  > explicit non-auto UserMode
  > Auto Lite probes
```

Mode semantics:

- `maintenance` -> `OFFLINE`;
- `work` -> `DRAINED`;
- `gaming` -> `DRAINED`;
- `idle` -> `FULL`;
- `force-ci` -> `FULL` while ignoring ordinary activity probes, but never bypassing hard safety;
- `auto` -> Auto Lite.

## 7. Zen override

Zen is **not** a seventh `UserMode`. It is a persistent override layered above the selected mode.

When Zen is enabled:

1. deny new CI admission immediately;
2. target `OFFLINE`;
3. if a worker is active, drain gracefully rather than killing it;
4. stop the listener after the active job completes;
5. suspend nonessential probes without changing configured enablement;
6. keep the minimal Agent/Tray/IPC shell alive so the user can resume;
7. persist Zen across restart;
8. when resumed, return to evaluation of the previously selected `UserMode`.

Zen is a human-exclusive pause, not an emergency termination feature.

## 8. Probe model

Policy consumes normalized evidence, never provider-specific implementation details.

Probe configuration and runtime observation are separate. Runtime states are `Active`, `Inactive`, `Unknown`, `Unavailable`, and `Suspended`.

Rules:

- observation failure is not `Inactive`;
- disabled is not `Inactive`;
- Zen suspension is not disabled;
- unknown safety evidence remains visible and explainable.

### User Activity Probe

Observes recent input, idle duration, and session state. It provides evidence for Auto Lite and diagnostics.

### Steam Game Probe

The requirement is to detect Steam actually launching an application/game, **not** merely `steam.exe` existing.

The initial Windows backend may use `HKCU\Software\Valve\Steam\RunningAppID` as local evidence. That registry value is an implementation detail, not a public Valve compatibility contract.

Expected interpretation:

- healthy non-zero AppID -> `Active`;
- healthy zero -> `Inactive`;
- source not applicable -> `Unavailable`;
- read/evidence failure -> `Unknown`.

The AppID may be exposed as evidence. Game-name resolution is optional and should remain local-only where practical. No Steam Web API is required.

### Process List Probe

A configurable list of executable names allows arbitrary latency-sensitive programs to be protected without recompiling RunnerMesh. v0.1 does not ship a universal application/game database.

## 9. Auto Lite

Auto Lite is intentionally conservative:

```text
hard safety failure                         -> no admission
Zen                                         -> OFFLINE / drain
explicit non-auto mode                      -> explicit mode semantics
Auto + any enabled activity probe Active    -> DRAINED
Auto + safety-relevant evidence Unknown     -> DRAINED
Auto + idle/away threshold satisfied
     + all relevant evidence permits        -> FULL
otherwise                                   -> DRAINED
```

If all useful automatic probes are disabled, `auto` resolves to `DRAINED`. The user may explicitly choose `idle` or `force-ci` to contribute capacity.

## 10. Tray contract

The tray is the primary daily UI. It is lightweight/native; v0.1 does not require Electron, a WebView application shell, or a TUI. A Rust stack such as `tray-icon` + `muda` + a Win32 event loop is acceptable.

UI mutation occurs only on the owning UI/event-loop thread. Background runtime work sends typed UI update commands.

Conceptual menu:

```text
RunnerMesh <version> · <channel>
Agent:       <health>
Capacity:    <NodeState> · <UserMode>
Runner:      <RunnerPhase>
GitHub:      <LinkState>

-------------------------
[ ] Zen Mode

Mode >
  Auto
  Work
  Gaming
  Idle
  Maintenance
  Force CI

Probes >
  [x] User activity       <runtime state>
  [x] Steam game          <runtime state>
  [x] Process list        <runtime state>

-------------------------
Status details
Doctor
Logs

Settings >
  Appearance > System / Light / Dark
  Language   > System / Simplified Chinese / English
  Start on login
  Auto idle threshold > fixed presets
  Check for updates automatically
  Open config
  Open data directory

-------------------------
Check for updates
Exit after drain
```

The tray icon represents capacity/`NodeState`, not only mode. Meaning must not depend on color alone; glyph/shape, tooltip, and menu text also carry state.

Probe entries show both configured enablement and runtime observation. Toggling a probe sends an `AgentCommand`; the tray never owns probe runtime state.

## 11. Theme and localization

`UiPreferences` includes:

- theme: `system`, `light`, `dark`;
- language: `system`, `zh-CN`, `en-US`.

Defaults are `system`. v0.1 ships Simplified Chinese and English.

Localization affects presentation only. Never localize JSON keys, serialized enum values, IPC command IDs, stable menu/action IDs, config keys, or machine reason codes. Visible strings must not be used as behavioral identifiers.

Theme/language changes must not alter admission, runner lifecycle, or probe configuration, and must not interrupt active CI.

## 12. Connection model

Do not model connectivity as one `remote_connected: bool`.

v0.1 has a typed `GitHub Actions` connection kind with states `Connected`, `Connecting`, `Disconnected`, `Unknown`, and `NotConfigured`.

A local process existing is not proof of remote connectivity. When evidence cannot prove link health, report `Unknown`.

A future RunnerMesh broker/control link is a separate connection kind and is not shown as if it exists in v0.1.

## 13. AgentSnapshot and machine contracts

All frontends render one authoritative `AgentSnapshot`, including build provenance, health, Zen, user mode, node state, admission decision/reason, runner phase, connections, probes, host observations, and effective UI preferences where useful.

- CLI renders text;
- `status --json` renders stable machine contracts;
- Tray renders icon/menu/tooltip;
- a future TUI may consume the same model.

## 14. Persistence

Persist intent/configuration, not reconstructable runtime facts.

Persist at least schema version, `UserMode`, Zen, probe enablement/process-list
configuration, Auto idle threshold, UI theme/language, start-on-login
preference, update preference/channel, the non-secret exact runner/selector
ownership binding, an opaque credential reference, and durable install/update
transaction receipts. Never persist a GitHub bearer token in normal JSON.

Reconstruct observed selector state, listener/worker PID, runner phase,
CPU/memory/idle observations, transient link/control state, and derived node
state after restart. Desired intent and observed remote/local state remain
separate.

Writes are validated, atomic, schema-versioned, and designed for transactional migration/rollback.

## 15. Official runner boundary and work-root invariant

RunnerMesh supervises the official GitHub Actions runner. It does not replace
workflow parsing, queue semantics, logs, checks, artifacts, or the runner
protocol. Local observation alone does not require a GitHub credential. The
accepted managed-admission architecture does require a separately configured,
OS-backed credential reference with the least documented exact-scope authority
to read and add/remove only the reserved label.

One execution identity owns one active work root. The same identity may reuse its own root; cross-identity active reuse is forbidden. RunnerMesh must not solve ownership conflicts by globally weakening Git `safe.directory` protections.

## 16. Graceful drain

The v0.1 product semantic is:

1. accepting Work/Gaming/Zen/drain records desired `DRAINED` and starts
   withdrawal immediately;
2. remove only `runnermesh-admit` from the exact configured runner and confirm
   its absence by readback;
3. do not kill or normally signal a `Runner.Worker` or Listener because the
   user chose Work/Gaming/Zen/drain/exit;
4. treat a racing assignment conservatively as in-flight and allow it to
   finish;
5. report achieved `DRAINED` only when the selector is absent, no exact bound
   Worker is active, and local evidence is consistent.

The GitHub label response/readback is not claimed as a globally linearizable
scheduler barrier without an upstream guarantee. Selector absence means no new
RunnerMesh eligibility for jobs that require the selector; already in-flight
assignments may still arrive and complete. Mutation/readback uncertainty or
failure reports withdrawing/blocked/unknown truthfully and never falls back to
destructive local shutdown.

Jobs intended for RunnerMesh-managed workstation capacity must include
`runnermesh-admit` together with their normal GitHub-native `runs-on` labels.
Generic-label jobs that omit it are outside the admission guarantee.

## 17. Restart and adoption

On startup the Agent observes existing local runner state, verifies execution identity, runner home, and work-root ownership, then adopts/reconciles when safe. It must not assume that a listener is unmanageable merely because the current Agent process did not start it.

This supports Agent crash recovery, tray restart, control-plane upgrade, and Windows resume/restart scenarios.

## 18. Source/build/release/runtime isolation

Repository invariant:

```text
SOURCE != BUILD != RELEASE != INSTALLED RUNTIME != ACTIVE VERSION
```

A mutable source tree or `target/` output is never the production deployment source. Autostart never points into a source tree. Production/dogfood installation comes only from an immutable release artifact or explicitly authorized immutable RC artifact.

## 19. Versioned installation and upgrade

Conceptual user-level layout:

```text
RunnerMesh/
  bin/              stable activation entry/shim
  versions/
    0.1.0/
    0.1.1/
    0.2.0-rc.1/
  current.json
  config/
  state/transactions/
  logs/
```

Frozen invariants:

- validated version payloads are immutable;
- activation selection is explicit and small/atomic;
- stable and staged/canary payloads may coexist, but only one Agent has control authority;
- config/data live outside version slots;
- rollback reselects a previous validated slot;
- source development cannot mutate installed stable runtime.

Update transaction:

```text
check
-> download/stage
-> checksum/artifact verification
-> compatibility validation
-> durable READY_TO_ACTIVATE
-> wait for safe activation point when required
-> activate
-> start / health-check / reconcile
-> commit receipt
-> rollback on failure
```

RunnerMesh update must not kill an active CI job. Control-plane-compatible updates may replace the Agent while leaving the official Listener/Worker untouched, followed by safe adoption. Execution-plane migrations defer until drained.

The official GitHub runner keeps its own supported update lifecycle; RunnerMesh must rediscover/reconcile rather than permanently pinning one exact runner binary.

## 20. Release and trust

Minimum v0.1 release:

- Windows x64 artifact;
- SHA-256 checksums;
- version/commit/channel/target provenance;
- user-level install;
- upgrade/rollback support;
- GitHub Release.

WinGet is desirable after v0.1.0 but is not a release blocker.

Public pull-request CI remains GitHub-hosted. Persistent personal workstations
must not execute arbitrary untrusted fork code by default. Trusted workstation
dogfood is a separate controlled lane.

Managed admission expands the v0.1 trust boundary to a narrow GitHub control
credential. For an organization runner the least documented fine-grained
permission is `Self-hosted runners: write`; for a repository runner it is
`Administration: write`. A provider-neutral secret-reference abstraction keeps
the bearer value out of normal JSON, snapshots, logs, and receipts. On Windows,
the product adapter uses Credential Manager, DPAPI-backed storage, or an
equivalent OS-backed facility. Creating, rotating, or revoking a real
credential remains an explicit Owner action.

## 21. Development trains

The roadmap-v3 implementation sequence is authoritative in
`goals/RM-V0_1-ROADMAP.md`.

- Train A (G02-G07): runtime contracts through probes/Auto Lite — autonomous;
- Train B1 (G08-G10): runner observer, supervisor core, host/recovery — autonomous and non-mutating to production runner;
- P0: supervised baseline restoration of the historical G11 experiment — Owner transaction, with no qualification continuation;
- G11R-A/B/C: admission architecture, lifecycle implementation, and qualification readiness — autonomous and non-mutating to the real runner;
- H1: one-shot real lifecycle qualification with automatic restore attempt — Owner transaction;
- G12-G15 source preparation: autonomous extraction/rewrite in sandbox roots
  may begin before H1, but acceptance and merge require H1 PASS and baseline
  restoration PASS;
- G15R: one integrated pre-H2 RC — autonomous, without production activation;
- H2/G16: real workstation cutover plus sustained dogfood — Owner transaction and release gate;
- G17: RC closeout — autonomous, without stable publication;
- H3/G18: public v0.1.0 publication — Owner transaction.

Historical V3/V4/V4R/V4S qualification variants are frozen evidence, not entry
points for new execution. Future work uses the accepted G11R architecture, one
readiness gate, and one H1 transaction family.
