# RunnerMesh v0.1 release operations

This document fixes the v0.1 artifact identity and the bounded verification,
cutover, rollback, and publication boundaries. It does not authorize a
production installation or a public release.

## Immutable candidate identity

The only v0.1 Windows package name is:

```text
runnermesh-0.1.0-windows-x64.zip
```

Its companion verification files are:

```text
runnermesh-0.1.0-windows-x64.zip.sha256
runnermesh-0.1.0-windows-x64.provenance.json
```

The provenance contract is version `0.1.0`, channel `rc`, target
`x86_64-pc-windows-msvc`, and one exact lowercase 40-hex authoritative-main
commit. The package manifest and `SHA256SUMS` bind every runtime member. The
outer `.sha256` file binds the exact archive bytes.

The `Immutable RC Candidate` workflow is manual, read-only to repository
contents, restricted to `main`, and requires the operator to repeat the exact
expected commit. It uploads artifacts but never creates a tag or release.

## Build and isolation

The workflow builds with `CARGO_TARGET_DIR` under the hosted runner temporary
root, packages into a separate release root, and leaves the source checkout
distinct from both. A sandbox extraction or installed version must use another
new explicit root:

```text
SOURCE != BUILD != RELEASE != INSTALLED RUNTIME != ACTIVE VERSION
```

Release builds set `RUNNERMESH_BUILD_COMMIT` and
`RUNNERMESH_BUILD_CHANNEL=rc`. The Agent snapshot must report the same version,
commit, channel, and target as the package provenance.

## Verification

From a trusted checkout of the same exact commit, verify the archive with the
release-built helper:

```powershell
runnermesh-package.exe verify C:\absolute\release\runnermesh-0.1.0-windows-x64.zip
runnermesh-package.exe extract C:\absolute\release\runnermesh-0.1.0-windows-x64.zip C:\new-absolute-sandbox-root
```

The `extract` destination must be a new absolute directory. The helper verifies
the archive, member names, member hashes, manifest, checksum file, provenance,
and size bounds before committing the sandbox directory.

Independently compare the public archive digest:

```powershell
(Get-FileHash -Algorithm SHA256 -LiteralPath C:\absolute\release\runnermesh-0.1.0-windows-x64.zip).Hash.ToLowerInvariant()
Get-Content -LiteralPath C:\absolute\release\runnermesh-0.1.0-windows-x64.zip.sha256
```

## H2 cutover boundary

H2 may use only the G15R-accepted archive and exact hash. Before mutation it
must display the exact commit, archive hash, owned installation root, current
user Startup entry, cutover actions, and rollback actions, then receive the
Master Goal H2 Owner token.

The accepted installation model uses immutable version slots, a stable Agent
entry, explicit active-version state, and a current-user Startup entry that
targets only that stable installed entry. Production mutation never uses a
worktree or Cargo `target/` binary.

## Rollback and recovery

Keep the previously active installed slot until the new Agent, Tray, CLI, IPC,
doctor, policy/probes, and required runner lifecycle observations pass.
Activation failure restores that prior slot. An interrupted install, update,
activation, or uninstall is reconciled from its durable transaction before a
new operation starts. Unknown ownership or transaction drift fails closed.

If H2 fails after mutation, restore the prior active slot and prior owned
autostart state before any further development. Never delete unrelated files,
reuse another identity's work root, or signal a normal active Worker.

## Publication boundary

G15R and H2 do not publish. After dogfood and G17 bind to these exact bytes,
H3 may publish only this previously verified archive and companion metadata.
Any downloaded-byte or hash mismatch blocks publication; rebuilding or
substituting an artifact silently is forbidden.
